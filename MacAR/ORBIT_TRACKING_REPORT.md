# 周回追跡の改善実験（2026-09-28）

## 結論

「対象の周囲を回りながら、正しい姿勢で途切れずMPRを見る」はまだ未達です。
短い遮蔽後の復帰と点補充を改善しましたが、**追跡率の上昇と姿勢精度の改善は同じではありません**。
反復試験では、従来より長くPASSする一方、誤った姿勢で追跡が継続する区間も増えました。
そのため今回の変更は、通常設定を置き換えず、明示選択する実験モードにしています。
合成試験の座標誤差はCT重畳精度・患者内部の位置精度ではありません。

## 試し方

1. VS Codeで `MacAR: Browser Live (3DGS + MPR)` を停止・F5で再起動。
2. ブラウザを再読み込みし、照合データを `3DGS · DINOv2 + ALIKED` にする。
3. 「3DGSの対応点更新」で **周回追跡・復帰強化（実験／精度未確認）** を選んで開始。
4. まずゆっくり回り、下部固定パネルの追加点数・復帰回数・姿勢修正・全体再探索を確認。
5. 比較するときは停止し、**追跡優先・バックグラウンド継続補充** に戻して開始。

通常設定は従来のままです。カメラ取得、AF、2000点上限、最低10 inliers・比率20%、
3DGS/XYZデータ、CT座標変換は変更していません。CLIでは3DGS validated・background経路に
`--tracking-orbit-recovery` を追加すると実験モードになります。

## 原因と対策

| 確認した問題 | 実験モードの対策 | 制限 |
|---|---|---|
| 1フレームの追跡失敗で点集合を捨てる | 最後のQC通過点を最大0.8秒保持し、最新画像で再追跡・PnP/QC | 最大6回。過去姿勢をそのまま表示しない |
| 短いロストでも毎回全体探索へ戻る | 直前2秒以内の姿勢に近いviewを一度だけ探索 | 旧姿勢はview選択用。新規PnPの姿勢拘束にしない |
| 探索結果の転送中に黒／ボケの1枚で点を失う | 悪い中間LKステップを飛ばし、最後に良好だった画像から再試行 | 最新画像へ到達しなければ拒否。最大8ステップ |
| 点が尽きる前の補充開始が遅い | 点数減少から枯渇が見込まれる場合、完了後待機を0.2秒まで短縮 | 同時1探索のまま。ロスト後待機は0.3秒 |
| 補充点を旧姿勢へ合わせるだけでドリフトを直せない | 新しい対応でPnPし、既存点と新規点の両方の残差を確認して姿勢修正 | 条件を満たした修正だけ、同じ現在フレームで再QC |
| 弱い旧点集合が強い新規対応を拒み続ける | 旧80点未満、新規60点以上かつ旧点数の2倍以上などの厳しい条件で再初期化 | 角度20°・位置100 mm以内。位置単位mm前提 |
| 強い新規対応と旧追跡の姿勢が食い違う | どちらも無条件に採らず、重畳停止・古い復帰点破棄・全体再探索 | 不一致を検出できない誤姿勢は残る |

姿勢修正の通常経路は変化12°/25 mm以内、旧点60%以上の一致、両点集合の頑健残差の改善、
既存QCを要求します。再初期化には新規inlier率50%以上、画面凸包2%以上、平均誤差3 px以下、
p95誤差5 px以下も要求します。これは正解姿勢の証明ではありません。

点配置から1 pxの独立観測ノイズに対する局所回転感度も計算しました。
世界座標系やmm/mの単位変更に依存しない診断値ですが、誤対応・XYZ誤差を含む実際の姿勢誤差とは
一致しませんでした。優先補充への適用も試しましたが、一貫した改善がなく取り下げました。
現在は診断値のみで、PASS閾値・補充トリガーには使いません。

## 再現用試験

`benchmark_orbit_tracking.py` が同じ3DGSを新しい既知カメラ軌道からRGB描画し、実際の非同期
追跡・照合コードへ入力します。参照画像の順送りではありません。

- 180枚、方位2°刻み、上方仰角35°±8°、960×720。
- 10 fps指定：約19.6秒で一周。6 fps指定：約31.5秒で一周。
- 60・61・120番の3枚を全面黒にして短い遮蔽を模擬。
- 焦点距離は既知。MPS使用。MPR描画・ブラウザ描画・カメラ伝送負荷は含まない。
- 初回位置合わせ後、ライブと同じく探索中も追跡を継続する。
- 非同期結果の到着タイミングが違うため、同じ映像でも反復結果は変わる。

最後に比較した記録（分母177は黒3枚を除く。各行1試行）：

| 条件・記録名 | PASS率 | 連続ロスト最大※ | 前景処理中央値 / p95 | 回転誤差中央値 / p95 |
|---|---:|---:|---:|---:|
| 通常・速め `pair1_before` | 67.2% | 3.1秒 | 10.7 / 24.0 ms | 1.79 / 4.30° |
| 通常・速め `pair2_before` | 61.0% | 3.5秒 | 9.5 / 21.4 ms | 1.89 / 6.66° |
| 実験・速め `guarded_fast` | 92.7% | 1.3秒 | 10.2 / 21.6 ms | 2.21 / 10.44° |
| 通常・ゆっくり `slow_before` | 77.4% | 3.83秒 | 11.8 / 37.5 ms | 2.07 / 4.22° |
| 実験・ゆっくり `guarded_slow` | 97.7% | 0.67秒 | 12.8 / 43.6 ms | 1.48 / 10.58° |

※連続ロストフレーム数÷指定fpsの名目値。実際の1周時間はJSONの`sequence_seconds`に保存。

全記録で黒フレームのPASSは0。実験途中には177/177を追跡できた試行もありましたが、
繰り返して再現しなかったため、100%追跡を達成したとは扱いません。

**悪化も確認しています。** 最後の速め試行は、角度誤差10°超のPASSが18/164フレーム、
カメラ位置誤差p95は142.8 mmでした。ゆっくりの試行でも10°超が16/173フレーム、
位置誤差p95は70.1 mmでした。通常と実験の両方がPASSした共通フレームだけでも、
回転誤差p95は速め4.31→10.44°、ゆっくり4.22→10.71°でした。
継続時間を伸ばした区間だけの問題とは言い切れません。最後の2試行では強い姿勢不一致ガードは
発動せず、現状のガードだけではこの誤追跡を防げませんでした。

参照とqueryが同じGS由来なので、実写との見え方差・近似XYZの物理精度・CT登録誤差は評価できません。
観測した位置差はカメラ中心の差であり、患者内部のTREではありません。

## ファイルと次の課題

最終の自動テストは **256件合格**。復帰期限、較正変更時の破棄、実LK/PnPによる黒フレーム後の復帰、
古い姿勢の非表示、転送の最新フレーム到達、姿勢修正と矛盾時の重畳停止、通常／実験モード切替、
ブラウザ表示・通信などを確認しています。JavaScript構文チェックも通過しました。
単体テスト合格は実ライブの成功率・位置精度を保証しません。この作業では実カメラを起動していません。

- `tracking_recovery.py`: 短時間の復帰点保持、較正・画像サイズの整合チェック。
- `replenishment_refinement.py`: 新規対応による姿勢修正、不一致判定。
- `glb_virtual_live.py`: 非同期探索と現在フレームへの転送・統合。
- `background_refresh.py`: 同時実行数・待機・負荷の制御。
- `pose_observability.py`: 点配置の局所感度（診断専用）。
- `browser_live.py` / `browser_ui/`: 実験モード選択、下部の実行状況。
- `benchmark_orbit_tracking.py`: 既知姿勢の周回再生と誤差記録。

次に優先すべきは、探索をさらに増やすことではなく、**繰り返し模様へ乗り移ったLK点を、
独立した実写／参照対応で検知すること**です。複数フレーム離れた対応の再確認や、追跡の観測と
独立再照合の観測を区別した信頼度管理が候補です。この報告の実験ではまだ実装していません。
現在の近似XYZと未校正カメラも、別途検証が必要です。
