# IMG_2598 / IMG_2590 写真照合の遅延調査（2026-10-05）

後続の探索調査で、ユーザー再起動前後の同じ2593の抽出21.65秒→0.83秒、最終姿勢一致を確認した。ステージ・サイズ・点数・GPUメモリ解放・LightGlue反復の追加結果は[探索調査](ALIKED_EXTRACTION_EXPLORATION_20261005.md)。以下は最初の調査時点の測定と制約として保持する。

## 結論と確度

直前の「既知RC姿勢を使う前処理」が、今回のライブ写真照合を遅くしたという証拠はない。実行中のMacARは10月2日の旧stage_48地図を使用し、新しい前処理地図を選択していない。ライブ経路では従来どおりALIKEDとLightGlueを読み込む。

遅延箇所は特定できた。IMG_2590は照合27.52秒のうちALIKED抽出区間20.12秒、LightGlue合計5.58秒、PnP合計0.069秒。IMG_2598は抽出区間に加え、最初の候補集合が不適切で候補拡張が必要になり、24回のLightGlue照合を実行している。

実行中プロセスのメモリ肥大化・退避が、抽出区間の異常な遅さの最有力候補。14:09のOS観測ではMacARのphysical footprintが19.3G、書き込み可能領域のswapped_outが19.1G。Macの物理メモリは16GiB、システム全体のswap使用量は23,364.75MiBだった。ただし取得は問題の照合後であり、**照合中のpage-inと遅延の同時計測・実行中プロセスの再起動前後比較は未実施**。スワップが20秒の直接原因とまでは確定していない。

## 条件

- ユーザーのIMG_2598.jpeg / IMG_2590.jpegの元ファイルを使用。24MP画像、写真特徴抽出サイズ1600、最大2000特徴点。
- 使用地図：`output_map_preprocessing/20261002-153042-c033a9/stage_48`。
- 3DGS粗検索dino-patch、top_k=3、登録写真候補adaptive、precision QC、FOV72°、MPRあり。
- 比較プロセスは同じvenv、現在の`runtime_arguments`と`localize_photo`を使用。MPS、torch 2.8.0、torch CPU threads=4。
- 実行中プロセスの起動設定はdevice=auto。実効deviceとtorch thread数は現在のJSONLには保存されていない。VS Code debugpyによる起動を確認。
- 別プロセス比較中もユーザーのMacARとChromeは動作。測定は各条件1回で、冷却状態やキャッシュ履歴を完全にそろえた厳密な性能試験ではない。
- 新旧コードの独立A/B試験ではなく、現在のコード・設定を別プロセスに再現した比較。

## IMG_2598の追加ボトルネック

1. top-3粗検索はview_0062 / 0064 / 0053を選び、そこから実写6枚を照合するがPASSに到達しない。
2. 同じqueryを使って同じ6枚をXYZ-onlyで照合し直すがFAIL。
3. 写真経路がtop-10へ拡張し、**ALIKEDも再抽出**。元の6枚を含む12枚を照合する。
4. 拡張候補7枚目の00199.pngが採用され、12枚目の00266.pngまで確認した後、adaptiveが停止する。

合計24照合（異なる実写は12枚）。LightGlue合計12.55秒、幾何検証1.01秒、PnP1.03秒。候補拡張時のquery再利用と、重複候補の照合再利用には改善余地がある。ただしXYZ-only照合は入力特徴集合が異なるため、全特徴照合結果をそのまま代用できない。候補拡張を無くしたりQCを弱めると、この写真は現在の条件でFAILのままになる。

## メモリの追加検証

OSのlive process VM summary：

- physical footprint 19.3G、peak 19.6G。
- writable swapped_out 19.1G（96%）、resident 235.7M。
- owned unmapped (graphics) 12.6G。
- MALLOC_SMALL 6.0G、MALLOC_LARGE 632.1M。

OS上のgraphics割り当てを、そのままPyTorchキャッシュの内訳と断定はできない。

調査用プロセスで同じ2590をモデル読み込み→照合→closeの順に4回繰り返した。使用中MPS tensorはclose後0となるが、driver allocationは約4.35GB残った。gc.collectだけでは減らず、torch.mps.empty_cache後97.4MBへ低下した。同じ写真の反復では無限の増大は再現せず、速度は約3.93秒→2.53秒→以降同程度だった。close後の別プロセスfootprintは2.9G、peak6.1G。

別の抽出のみの比較では、2598/2590のcrop比率と、2593/2594の異なるcrop比率を処理すると、使用中tensorは約145MBでほぼ一定のまま、driver allocationは4.36GB→6.51GBへ増えた。cleanup後empty_cacheで134MBへ低下した。**入力crop形状の変化によって未使用のGPU割り当てが増える現象は再現した**。しかし、実行中の19.3G全量の内訳や、どの履歴で肥大化したかは未確定。

CPU抽出比較も実施し、2598は初回2.28秒、後続1.50/1.28秒。CPU・4 threadsという条件だけでも20秒は再現しなかった。実行中の実効deviceが未記録なので、この比較でCPU選択を直接否定するものではない。

## 次に確定すること

測定状態を保持・保存した上で、同じMacARの再起動前後に2590を比較し、照合中のprocess footprint / page-in・swap-inとMPS current/driver allocationを同時記録する。ここで抽出20秒が消えるかを確認するのが、因果関係を確定する最短の試験。現在の固定姿勢・測定点を失う操作になるため、本調査では実行中アプリを再起動していない。

調査終盤の確認では元PID83878が終了し、元ポート60937への接続も切れていた。最後のruntime記録は14:16:11のcontrol。ユーザーから「閉じる・再起動する操作をした」と回答があり、終了操作が行われたことを確認した。調査側から元プロセスへの終了・再起動命令は送っていない。再起動後の同じ写真を未計測なので、この終了をメモリ問題の解決確認としては扱わない。調査用workerはすべて終了を確認した。

改善案は、写真切り替え・モデル終了時の不要MPS割り当て解放、crop入力形状の種類を抑える方式、2598候補拡張時の重複計算再利用。まずメモリ計測付きで効果を検証する必要があり、単にLightGlueやQCを外す変更は本調査の結論ではない。
