## ブラウザでライブ・3DGS・MPRを操作する（新しい表示UI）

### 継続補充と視点イベント（2026-10-22）

バックグラウンド更新は、同じ視点でも待機・負荷管理付きで近傍補充を続けます。物体を見る方向の4°変化から先行起動し、従来の12°条件・新しい投影区画・追跡支持の悪化も維持します。ロールだけを視点変化とは数えません。同時1探索・定期全体確認・PnP/QCは維持。10/4〜10/21の「安定した同一視点では補充を停止」は履歴です。新領域の判定は地図投影による予測で、遮蔽を保証しません。[現行仕様と検証条件](docs/regional-replenishment.md)・[視点イベントの定義](docs/viewpoint-refresh.md)。

### 登録実写の候補採点（2026-10-04）

登録実写の初期照合・全体再探索では、対象cropの共通8×8領域を各最大1票とし、領域内の再投影誤差で減点した合計で姿勢候補を選びます。密集領域のinlier数による水増しを抑え、早期終了・競合判定も同じ点数へ揃えます。全点のPnPと既存QCは維持します。比較用の3DGS仮想画像経路は対象外です。[採点仕様・検証条件](docs/spatial-pose-scoring.md)を参照してください。

### 照合と特徴点追跡を並行する（2026-10-03）

ライブではALIKED抽出直後の点を、LightGlueと前景の2D LK追跡へ同時に渡します。照合が進む間も元の点との対応を保持して毎処理フレーム追跡し、照合完了時に生き残った点へXYZを付与します。追跡中は現在画像の新旧共通集合で姿勢を選び、初期化/復帰は独立した現在PnPを行います。既存QCと最終確認を通した後だけ、姿勢表示・追跡点更新へ使います。登録実写と3DGS参照の双方が対象で、静止写真照合は追跡しません。

連続追跡で最新フレームに到達し、現在画像でPnP/QCを通った結果は、照合時間が10秒を超えても利用できます。追跡していない結果の年齢上限（ブラウザ10秒、CLI既定5秒）は維持します。追跡断絶・画像サイズ変更・reset・照合FAIL・現在画像のQC失敗を引き継ぎで隠しません。2D追跡中だけではモデルに対する絶対姿勢は未確定です。

ALIKED抽出が終わるまでのフレームは既存の有限バッファで橋渡しします。抽出自体に長時間かかる問題、遮蔽による点の消失、初期照合の誤りはこの変更だけでは解消しません。実機確認ではカメラを動かしながら照合を遅延させ、`query_tracking` / `seed_transport` の残存点・現在PnP/QC・引き継ぎ時間を確認します。実装の検証結果は [CONCURRENT_TRACKING_20261003.md](CONCURRENT_TRACKING_20261003.md) に記録します。

alpha参照のRGB置換実験は `python3 gs_render_compare.py --reference-output 新しい出力接頭辞` で生成を明示的に有効化し、画面の「alpha 1.0対照と1.5参照を生成」を押します。元のカメラ・XYZを保ち、再描画1.0／1.5を別フォルダへ保存します（既存出力の上書き不可）。`evaluate_alpha_references.py --photo-root 検証写真の親フォルダ --output 新しい結果フォルダ` は、元参照／対照1.0／1.5を、登録実写・3DGSそれぞれで写真照合します。標準はMac GPU、HFOV 72°、写真入力1600 px、厳格QC、Top-3（失敗時Top-10再試行）。写真の真値姿勢がない場合、QCのPASS率と再投影誤差はCT位置精度ではありません。

比較対象フォルダは `--original`・`--alpha10`・`--alpha15` で指定できます。カメラとXYZが同一であることを開始前に検査します。既定は2026-10-03の128-view RGB比較セットです。CPUで照合成績を確認する場合は `--device cpu` とし、Mac GPU実測との時間比較はしません。

### 登録実写の前処理をブラウザで確認・増補

ブラウザの「照合データ」の直下に **登録実写の地図** を表示します。既定では同じ登録データ（Images/Cameras/splat）の保存済み・幾何監査合格地図から、XYZ付与率、XYZ観測数の順に推奨地図を選びます。未監査・保存後に変更された地図や別オブジェクトの地図は自動採用しません。手動で「この地図を使用」と指定した選択は優先します。推奨は地図の充実度でありCTの実測精度を保証しません。

**「地図ファイルを選択…」** でMacの選択画面から `object_aliked_map.npz` または `summary.json` を選択します。地図フォルダ・全参照特徴は関連付けて読み込むので、ファイルを個別にアップロードしたりパスを入力する必要はありません。「推奨地図に戻す」で推奨結果へ戻せます。CT・座標metadata・校正・3DGSのmanifestも「登録データ・校正ファイル」内の選択ボタンで指定できます。前処理画面にも地図ファイル選択があります。変更は停止中に行い、開始で適用します。実行中のカメラ／AFや前処理ジョブは自動停止・再起動しません。

VS Codeの **MacAR: Browser Live (3DGS + MPR)** をF5で起動し、左上の **「登録実写の前処理・特徴点／XYZを確認」** を開きます（同じサーバーの `/preprocess`）。カメラを開く必要はありません。参照ごとの付与率・不足一覧、実際の対象crop／マスク輪郭、ALIKED全点（橙：XYZなし／緑：XYZあり）、点ごとのXYZと再投影誤差、3Dランドマーク、カメラ方向の分布を確認できます。拡大・移動も可能。「全XYZの幾何監査」は元地図を変更せず全点を登録カメラへ再投影します。

前処理画面は **①確認中の保存済み地図／②現在の処理（停止中は最新結果）／③過去の履歴** を分離します。12→24→48枚の段階カードに、未着手・現在段階・監査合格保存済みを表示。現在処理は読込→照合→XYZ確定→保存→監査の順に示し、バーはその処理だけの件数・割合（画像ペア／トラック／登録画像）です。全体の所要時間比やETAではありません。保存済みXYZ付与率は別欄で、処理進捗とは区別します。元地図からの付与率改善、照合キャッシュの再利用数、新規計算数も表示。過去のジョブIDは折りたたみ内に移し、表示更新で履歴を閉じません。ファイル保存だけで完了扱いにせず、幾何監査合格後の段階だけ使用可能として表示します。計算内容・QCは変更しません。

**「全登録画像 → 不足画像を重点処理」＋最大48枚** は、全画像を12近傍で照合し、付与率目安未満またはXYZ300点未満の画像を24→48近傍で再処理します。目安は重点処理の選択条件で、幾何QCを緩めません。新規XYZは3画像以上・視差2°・再投影最大3px、既存XYZへの追加観測は独立2画像以上の支持を検証します。元ID／XYZを保持し、各段階を `output_map_preprocessing/JOB/stage_XX` に保存し、全点の幾何監査を行います。十分な対応を得られない画像はゼロ／不足として残します。「完了」は全点へのXYZ付与やCT位置精度の保証ではありません。

全画像の照合は数十分〜数時間かかる場合があります。処理中のライブ開始は競合防止のため禁止します。ジョブは独立したPythonプロセスで実行され、ブラウザを閉じても続行します。「中止」は安全な区切りで止まり、元地図・完了段階・照合キャッシュを保持します。特徴内容とRCカメラ内容をハッシュしたpair cacheを次のジョブにも再利用するため、再実行でも一致済みの照合をやり直しません。中断した段階の未完了地図は選択できません。

2026-10-02 前処理の幾何計算を高速化：固定RCカメラ・画像全特徴の歪み補正をジョブ内で再利用し、最大32個の三角測量seedをまとめてSVD／再投影します。seedの順序、最低3視点・視差2°・最大再投影3 px・対象領域・既存ID/XYZの保持条件は変更しません。OpenCVで歪みを扱い、書き出し時の全XYZ再投影も画像単位にまとめます。進捗／レポートに `geometry_engine=prepared-batched-v1` と `triangulation_seconds`、`export_seconds` を記録します。**実行中プロセスには適用されません。一時停止・再開も旧コードのままで、新規ジョブから適用されます。** 現在の進捗を失わせる自動再起動は行いません。

## 登録実写からobject-only ALIKED 3D地図を生成（実験）

対象物だけを含む3DGS PLY、登録済みCOLMAP画像、`Images.txt`、`Cameras.txt`を使います。PLYを各登録画像へ投影して対象物を自動マスクし、その領域に残るALIKED特徴を、固定RC姿勢によるエピポーラ候補制限とdescriptor照合で複数画像間対応させます。各特徴のXYZは**PLYのGaussian位置や近似depthから読み取らず**、固定したRC/COLMAPカメラ姿勢と実写画像上の対応位置から三角測量します。PLYは対象物だけを含むことが前提です。データセット内の`scene_transform.json`があれば`world_from_train`を使ってPLY座標をCOLMAP座標へ戻します。今回のデータではこの変換は恒等です。比較用LightGlue方式は `--matching-method lightglue`、新規定は `--matching-method known-pose` です。

```bash
cd /Users/daisuketanii/Documents/GitHub/UXbrowse/MacAR
source .venv/bin/activate
python3 build_aliked_object_map.py \
  --dataset-root "/Users/daisuketanii/Library/CloudStorage/GoogleDrive-mp.daisuketanii@gmail.com/マイドライブ/010_splat/data/260918splat" \
  --output output_aliked_object_map
```

`--dataset-root`内の`splat.ply`、`colmap/images`、`colmap/sparse/0/Images.txt`、`Cameras.txt`を一組として読みます。別の対象物ではrootを変えます。配置が異なる場合のみ`--image-dir`、`--images`、`--cameras`、`--splat`で個別に上書きします。異なる撮影データのPLYとカメラ姿勢を誤って混ぜないよう、rootまたは全個別パスの指定を必須にしています。最初は`--max-images 24 --output /private/tmp/aliked_object_pilot`で少数画像のマスクと三角測量を確認できます。出力先は空である必要があります。

出力の`reference_features/*.npz`には、登録画像ごとにALIKED特徴、画像全体の`full_uv`、対応が確定した特徴の`point_ids`と`xyz`を保持します。未確定の特徴は`point_ids=-1`です。登録実写の局所照合は、保存済みのobject-only ALIKED全特徴をLightGlueへ渡し、面除外・幾何検証の後に`point_ids >= 0`かつ有限のXYZを持つ対応だけをPnPへ渡します。XYZ未登録の特徴に近傍点や3DGS depthを代入しません。全特徴の照合がXYZ不足で失敗した場合は、同じライブ特徴・ROI・参照候補を再利用し、従来のXYZ付き特徴だけの照合を再試行します。十分な採用点がある姿勢を曖昧性等のQCで落とした場合は、この再試行を行いません。既存のPnP/QC閾値は変更していません。ここでの`point_ids`は新しく三角測量したALIKEDランドマークの番号で、元COLMAPの`POINT3D_ID`とは別物です。`object_aliked_map.npz`は三角測量したXYZとトラック長、`object_aliked_observations.csv`は画像↔特徴↔3D点の表、`summary.json`は処理件数と再投影誤差、`mask_qc/`はマスク・採用点の確認画像です。低い再投影誤差だけではCT/実物上の位置精度を保証しません。

登録実写の検証ログには参照特徴総数・XYZ付き特徴数・照合後のXYZ未登録数・重複除去数も表示します。ブラウザ検証画面では、XYZ付き再試行の有無と採用結果を区別します。この変更に地図の再生成は不要です。通常の3DGS仮想画像モードは変更していません。

### CT／ライブ画像の表示一致性を検証する

同じGUIで①「CT重畳の表示ずれを測る」を選び、**この登録地図と対応する**CT `.mha` と座標メタデータを詳細設定で確認してから起動します。既定のCTファイルは既存の`260911`データであり、フォルダ名や範囲が近いだけでは同じCT座標への登録精度は証明できません。必要ならiPhoneの校正`.npz`も指定します。未校正の場合、表示されるmm値は既定の水平画角72°から推定した内部パラメータに依存する探索的な値です。

2. 通常クリックで、可視光画像のマーカー中心を指定します（シアン）。CTで同じマーカーが見えるスライスまで動かし、`Shift`＋クリックでCTマーカー中心を指定します（マゼンタ）。拡大スライダーを変えても選択点は元画像画素／CTの3D物理座標として保持されます。
3. 画面には投影位置の差（px）と、選択したCT点の深さにおける視線からの横方向距離（mm）を表示します。`N`でCT点のスライスへ戻し、`S`で`output_ct_validation/measurements.csv`へ追記、`R`でライブPnPに戻ります。`Q`／`Esc`で終了します。

このMPRは固定カメラ姿勢に正対した斜断面です。CT点は元ボリュームの`Origin`・`TransformMatrix`・`ElementSpacing`から3D物理座標として求め、スライス変更後も同じ点を指します。マーカーが現在のスライスから離れた場合は`off-slice`距離を表示します。**単眼カメラのクリックだけから奥行きは決められない**ため、mm値はCT点の深さでの横方向の表示ずれであり、3D target registration errorや臨床精度ではありません。少なくとも複数マーカー、複数視点、校正済みカメラで分布を記録してください。

2026-09-25の`260918splat`実行結果：登録621枚中620枚で特徴を抽出し、17,973個の三角測量ランドマークと91,346件の観測を得ました。`00224.png`は指定した近傍姿勢・視差条件を満たす画像ペアがなく、対象外です。採用点の最大再投影誤差の中央値は1.79 pxでした。これは内部整合性であり、CT/実空間の絶対精度ではありません。

## Step 1: OBBで抽出

Euler角を度で指定する例：

```bash
python3 object_point_filter.py filter \
  --center Cx Cy Cz \
  --size Sx Sy Sz \
  --rotation Rx Ry Rz \
  --preview \
  --visualize
```

回転規約は入力座標内で`R = Rz @ Ry @ Rx`となる、ローカル座標からワールド座標へのactive rotationです。RC入力の場合はこの回転へRC→COLMAP変換を合成します。点の判定時には変換後の`R^T (p - C)`でローカル座標へ戻します。角度の既定単位は度です。ラジアンの場合は`--radians`を追加してください。

回転行列を直接指定する場合は、ローカル→ワールドの直交行列をrow-majorで9値渡します。

```bash
python3 object_point_filter.py filter \
  --center Cx Cy Cz --size Sx Sy Sz \
  --rotation-matrix R00 R01 R02 R10 R11 R12 R20 R21 R22
```

## Step 4: オフラインSIFT Matching / RANSAC-PnP試験

まず既知姿勢を持つ参照画像をクエリとして使い、その画像自身から登録されたdescriptorだけをFeature Mapから除外するleave-one-image-out試験を行います。他画像から得たdescriptorだけで再localizeし、RC姿勢との誤差を測定できます。

```bash
python3 offline_pnp_test.py \
  --query-image 00414.png \
  --query-image 00366.png \
  --query-image 00240.png
```

処理内容は、クエリ画像のSIFT抽出、Feature MapとのFLANN matching、異なる3D点を使ったLowe ratio test、3D点の重複排除、RANSAC-PnP、inlierによるLM pose refinementです。同一クエリ画像由来のmap descriptorは既定で除外します。

既定の合格条件は次の通りです。

- Lowe ratio: 0.75未満
- RANSAC再投影誤差: 4px以内
- PnP inlier: 20点以上
- inlier率: 20%以上

出力は`output_colmap_image/pnp_test/`へ作成します。

- `localization_results.csv`: 画像別の成否、match数、inlier数、推定姿勢、既知姿勢との誤差
- `localization_matches.csv`: PnPへ渡した2D–3D対応と再投影誤差
- `localization_summary.txt`: 全体集計と画像別結果
- `qc/*_pnp.jpg`: 緑がRANSAC inlier、赤がoutlierの重畳画像

### 本当に新しく撮影した画像

`Images.txt`に存在しない画像には既知のカメラ内部パラメータがないため、`fx fy cx cy`を明示します。この場合は正解姿勢がないため、inlier数・inlier率・再投影誤差で成否を判定します。

```bash
python3 offline_pnp_test.py \
  --query-dir /path/to/new-images \
  --query-image query.jpg \
  --intrinsics FX FY CX CY \
  --distortion K1 K2 P1 P2 K3
```

新規画像をリサイズ・クロップ・回転した場合は、その画像に対応する内部パラメータも同じpixel geometryへ変換する必要があります。

## Reference-guided PnP静止画PoC

Feature Map全体への直接matchingでは反復模様の誤対応が増えるため、登録画像を介して2D–3D対応を作る静止画PoCを追加しています。

```bash
python3 reference_guided_pnp.py \
  --query /Users/daisuketanii/Downloads/IMG_2532.jpeg
```

処理は、候補登録画像の検索、live–reference SIFT matching、Fundamental Matrix RANSAC、POINT3D_ID転写、暫定姿勢または登録画像姿勢からの投影近傍再探索、RANSAC-PnPの順です。異なる候補画像の対応を無条件に混ぜず、最もPnP inlier支持が多い単一姿勢仮説を最終結果として選びます。

既定の`IMG_2532.jpeg`では、従来のglobal matchingが0〜7 inlierだったのに対し、登録画像`00314.png`を経由した仮説で71 correspondence中36 inlier、inlier率0.507、平均inlier再投影誤差3.44pxとなり、20 inlier / 0.20の条件をPASSしました。これは近似画角65度での成立確認であり、絶対的な位置精度を保証するものではありません。

出力は`output_colmap_image/reference_guided_pnp/`です。

- `summary.txt`: 最良姿勢とTop-K比較
- `reference_results.csv`: 候補画像ごとの検索・幾何検証・PnP件数
- `best_guided_matches.csv`: 最良仮説の2D–3D対応、再投影誤差、inlier判定
- `best_guided_overlay.jpg`: query画像上のinlier（緑）とoutlier（赤）
- `best_pose.npz`: `rvec`、`tvec`、近似camera matrix
- `qc/`: live–referenceのFundamental Matrix inlier表示

このPoCはまだ`realtime_pnp.py`へ接続していません。まず静止画で候補選択と姿勢仮説の成立を確認するための実装です。

## Step 4.5: GLB仮想Reference + ALIKED/LightGlue試験

```text
GLB → 仮想Reference RGB/depth/XYZ
ライブ相当の静止画 → SIFTでReference候補検索
→ ALIKED + LightGlue → Fundamental RANSAC
→ Reference画素のGLB XYZを転写 → RANSAC-PnP + LM
```

使用するモデルは`data/260911/260108-3.glb`です。学習済みモデルとレンダラーの追加依存を一度だけ導入します。


### 72 View生成とライブ実行

VS Codeの「実行とデバッグ」で、次の順に起動します。

1. `MacAR: Generate GLB Reference Views (72)`
2. `MacAR: GLB ALIKED LightGlue Live (72 Views)`

72 Viewは方位12方向、仰角−30/0/+30度、距離2段階で生成されます。ライブ処理は72枚すべてへLightGlueをかけず、各フレームのSIFT投票でTop-3を選択してからALIKED + LightGlueを実行します。Top-3から得た対応は、同じライブ特徴点の競合をLightGlue scoreで解決して統合し、個別候補と統合候補のうち再投影誤差が正常な最良PnPを採用します。姿勢がPASSした後は、その2D–3D inlierを既存のLucas–Kanade Optical Flowへ渡して追跡し、150処理フレームごと、または追跡点が8点未満になったときにGLB Reference検索へ戻ります。

Terminalからの同等コマンドは次です。

```bash
python3 generate_glb_reference_views.py \
  --glb ../data/260911/260108-3.glb \
  --output output_glb_reference_views_72 \
  --azimuths 12 \
  --elevations -30 0 30 \
  --distances 2.5 3.3 \
  --width 960 \
  --height 720

python3 main.py \
  --camera 1 \
  --matching-mode glb-track \
  --glb-views output_glb_reference_views_72 \
  --glb-top-k 3 \
  --glb-max-keypoints 2048 \
  --glb-resize 1024 \
  --glb-match-threshold 0.01 \
  --max-processing-width 1280 \
  --process-fps 15 \
  --ransac-threshold 8 \
  --iterations 10000 \
  --min-inliers 10 \
  --tracking-reseed-frames 150 \
  --tracking-min-points 8
```

GLBの画素XYZはRC/GLB座標から既存MPRが使用するCOLMAP座標`(x, -z, y)`へ変換してからPnPへ渡します。そのため、PASS後の姿勢を既存MPR rendererへそのまま入力できます。画面上では初回・再探索時に`GLB ALIKED+LightGlue`、追跡中は`optical-flow tracking`と表示されます。

比較用として、従来のSIFT global Feature Map経路と、RC登録画像をReferenceにする`reference_guided_pnp.py`は削除していません。GLB方式はライブカメラ、Optical Flow追跡、既存MPR rendererへ接続済みです。

### 3DGS PLYからのライブPnP + MPR

二段階方式（view選択→local matching→XYZ→PnP→QC）は維持しています。
現在のライブ設定は元の`output_3dgs_reference_views_72_upper_negz_v2`です。ブラウザから同じカメラ／XYZを持つアルファ1.5参照も選べます。3DGS RGBと、近似depthを画素の視線上へ逆投影したXYZを使用します。穴の近傍XYZ流用・depth不連続を除外します。これは画素とXYZの不整合の修正であり、depthが実物表面と一致する保証ではありません。

`generate_3dgs_reference_views.py`には同じGaussian描画からRGBとdepth momentsを取得する実験経路も実装しました。scale/quaternion/opacity/SHを含むRGBと同じfootprint・alpha・順序で深度を合成します。ただし、透明度合成depthは表面depthではなく、今回の検証では誤差や対応不足が出たため、ライブの既定にはしていません。詳しくは`SPLAT_PIPELINE_AUDIT.md`を参照してください。

データ`260918splat/splat.ply`のXYZはすでにCOLMAP/MPR座標系です。GLB用の`(x, -z, y)`変換は適用せず、manifestの`runtime_transform: identity`で明示します。

VS Codeでは`MacAR: 3DGS DINOv2 Auto ROI Upper Live`を起動します。SIFT比較用の`MacAR: 3DGS ALIKED LightGlue Live (128 Upper Views)`も同じupper参照マップを読みます。現在の128視点は生成済みで、ライブ前に生成処理を実行する必要はありません。

このVS Code設定では、PASSしたPnP姿勢から実際の3DGS Gaussian RGBを描き、ライブカメラの隣に表示します。見え方の一致を確認するための**表示専用**で、描画結果は対応点探索・PnP・MPR姿勢には戻しません。既存の事前描画72視点とは異なり、カメラの推定6DoF姿勢から毎回描きます。98 MBのPLYをChrome/PlayCanvasへ起動時に一度読み込み、640幅・最大5 Hzで別プロセス描画します。3DGSパネルは3D点群マップの更新周期とは独立に更新されます。既知の参照姿勢での実測では、描画待ちを1フレームに短縮しても保存画像との差は平均0.13階調値で変わらず、1枚約115〜126 ms（うちスクリーンショット約109〜114 ms）でした。これは静止した既知姿勢での測定で、iPhoneライブでの実効FPSやPnPへのGPU負荷は未計測です。負荷が高い場合は`--gs-pose-render-hz 2`へ下げるか、`--show-gs-pose-render`を外すと従来表示へ戻せます。Node.jsとGoogle Chromeが必要です。投影はカメラ中心を主点とし、レンズ歪みは再現しないため、位置合わせ精度の証明には使えません。

3DGSライブの点補充は、既定で固定周期ではなく**追跡中のPnP inlierの3D分布**で発動します。毎処理フレーム、互いのXYZ間距離が30 mm以上で、最長辺に対する高さが15 mm以上の三角形を作れる3点が存在するか確認します。不足した場合、既存のPnP姿勢に近い仮想カメラへバックグラウンド照合し、独立PnP・姿勢一致・現在フレームへの光学フロー・再投影誤差・重複除去・QCを通った点だけを追跡集合へ追加します。検索中も追跡を継続し、検索は同時に1件のみ、完了後に最低1秒の間隔を置きます。補充条件はPnPのPASS判定の代わりにはなりません。座標単位はmmを前提とします。従来の150フレームごとの全体再探索も維持します。

設定は`--tracking-replenish-mode coverage --tracking-replenish-distance-mm 30 --tracking-replenish-height-mm 15 --tracking-replenish-cooldown 1`です。3D分布不足に加え、inlierの画像上の凸包が画面の2%未満、または最後に点を確認した姿勢から物体を見る方向が12度以上変わった場合、新たな投影領域が増えた場合も補充します。調整は`--tracking-replenish-image-coverage 0.02 --tracking-replenish-angle 12`です。従来の周期方式は`--tracking-replenish-mode interval --tracking-replenish-frames 30`、補充を無効にする場合は`--tracking-replenish-mode interval --tracking-replenish-frames 0`を指定します。検索理由は`replenish: 3d_support / image_coverage / view_direction_changed / new_regions_visible`、点が増えたときは`pose-guided replenishment: +N points`とコンソールに表示されます。[現行の補充仕様](docs/viewpoint-refresh.md)。

追跡中の姿勢ガイド補充では、ALIKEDの画像解像度は維持したまま、ライブ特徴を空間的に分散する最大1024点へ選別します。参照特徴のXYZは既存のgeometryから特徴点ごとに一度取得してRAMにキャッシュし、現在姿勢で正の深さ・ライブ画像/ROI範囲内に投影されるものを選びます。ライブ特徴の近くに投影される点を残し、参照側も最大1024点へ分散選別します。厳密な遮蔽判定ではなく、同一面が見えることを保証するフィルタでもありません。LightGlue後も、予測投影位置から96 px以内の対応だけを幾何検証・PnP・既存QCへ渡します（crop座標ではなく元画像座標）。

最も近いviewから順に照合し、既存QC、最低20 inliersかつinlier率50%以上、平均再投影誤差3 px以下（既存上限がより厳しければその上限）、現在姿勢との差5度/10 mm以内、30 mm/高さ15 mmの3D支持をすべて満たした場合だけ早期終了します。不足すれば次のviewへ進み、最終的に失敗すれば、同じ候補を従来の点数・投影制限なしで再照合します。この再試行時は処理時間が増えます。初期探索・全体再探索は従来通り2048点/Top-K比較と曖昧性QCを維持します。設定は`--virtual-guided-features 1024 --virtual-guided-radius 96`、従来方式との比較は`--virtual-guided-baseline`です。速度改善は追跡中の補充経路が対象で、CT位置精度改善を証明するものではありません。

補充時は`aliked_query.py`でALIKEDのdense map・検出点を一度作り、空間選別した1024点だけdescriptorを計算します。再試行では同じ画像のROI・dense map・計算済みdescriptorを再利用し、残りのdescriptorだけ追加します。参照側とライブ側の座標変換は従来と同じで、学習済み重みと画像解像度も共通です。一時的にdense mapを保持するため、その分だけRAMを使います。比較用の`--virtual-guided-full-descriptors`は全descriptor生成後に点を選別します。コンソールとdiagnosticsの`query_extraction_stages_ms`にdense/detection・descriptor時間、計算点数、再利用有無を記録します。内部区間時間はwall-clockで、GPUの区間ごとの同期は強制していません。CPU比較の区間時間とGPU実行時の区間時間は区別してください。

探索中の表示用DINO検索を抑え、完了した全体検索のview/crop結果を表示へ共有します。遅れて届く表示用検索が新しい結果を上書きすることも防ぎます。探索結果の点は、最大48枚の処理済みグレーフレームを保存し、最大8段のforward/backward光学フローで現在画像へ移します。途中で整合しない点は除外し、姿勢と追加点の採否は現在画像の既存PnP/QCで決めます。画面更新のためのフレームを使うため、カメラ取得コードは共通です。仮想画像のvalidatedモードは平均再投影誤差に加えて95パーセンタイルも確認し、平均誤差上限の1.5倍を超える場合は`reprojection_tail`として棄却します（既定9 px）。これらは画像空間の品質判定です。

### −Z上方視点・自動ROIを使う新しい実験経路

この患者モデルの実際の上方向は**−Z**です。旧72視点は`+Z up`として描画され、上方視点のつもりで下面を見ていました。新しい`output_3dgs_reference_views_72_upper_negz_v2`は`--up-axis negative-z`で、仰角0°/25°/50°に各12方位×2距離、計72視点を作成しました。これは**撮影位置とカメラの画面上方向だけ**の変更で、PLY・画素XYZ・COLMAP/CT座標への変換は行いません。ライブの3DGS姿勢ビューもmanifestの`up_axis`を読んで−Zを画面上へ表示します。

2026-09-30に上方65°の12方位×2距離（24視点）を追加し、96視点にしました。続いて真上90°から画面内回転を22.5°刻みで16方向×2距離（32視点）追加し、**現在のmanifestは128視点**です。0°/25°/50°/65°の既存96視点・view IDは保持しています。互換性のためフォルダ名には`72`が残ります。元のmanifestは同フォルダの`manifest.before_72views.json`、真上追加前は`manifest.before_96views.json`に保存しました。追加画像も既存と同じPLY、PlayCanvas RGB、ray-legacy-depth XYZ、−Z上方の条件で生成しました。真上カメラは位置を固定したまま画面内だけを回転し、RGBとXYZに同じカメラ姿勢を使います。

## Step 5: iPhone連係カメラでリアルタイムPnP + MPR

iPhoneをmacOSの連係カメラとして接続すれば、専用iOSアプリや画像転送サーバーは不要です。OpenCVがMacのカメラ入力を直接読み、SIFT matching、RANSAC-PnP、MHAのoblique MPR生成、カメラ画像への重畳までMac上で行います。

### VS Codeから起動

Terminal起動時とVS Code起動時でiPhoneのフォーカス挙動が異なる環境では、リポジトリの`UXbrowse`フォルダをVS Codeで開き、「実行とデバッグ」から`MacAR: Realtime PnP Main`を選んで起動します。この構成は`MacAR/.venv/bin/python3`、作業ディレクトリ`MacAR`、カメラ1、OpenCV/AVFoundation直接読取、ネイティブ解像度、フォーカスゲートなし、global Feature Map matching + temporal trackingを固定します。

Mainでは、最初にSIFTをFeature Map全体へ照合してRANSAC-PnPを実行します。PASSした2D–3D inlierはPOINT3D_IDを維持したままLucas–Kanade Optical Flowで次フレームへ伝播し、forward/backward誤差でドリフトを除去して、前回姿勢を初期値に高速PnPを実行します。10追跡フレームごと、または追跡点が10点未満になった時だけglobal matchingで点を補充・再localizeします。global再取得が1回失敗しても有効な追跡は破棄しません。通常のMPR表示条件はinlier 10点以上かつinlier ratio 20%以上です。

追跡なしで各処理フレームを都度走査する場合は`MacAR: Global Scan PnP (No Tracking)`、reference-guided方式を比較する場合は`MacAR: Reference Guided (Experimental)`を選びます。Terminalでは`python3 main_global_scan.py --camera 1`で起動できます。この経路は毎回SIFT抽出、Feature Map全体とのmatching、RANSAC-PnPを実行し、前フレームの点や姿勢を再利用しません。

切り分けには`MacAR: Simple Camera Focus Test`、RAWとPnP画面の同時比較には`MacAR: Realtime PnP + RAW Compare`を使用します。VS Codeの統合Terminalから起動するため、カメラ権限もVS Code側の条件に揃います。

### 1. カメラ番号を確認

iPhoneを連係カメラとしてMacへ接続した状態で、`MacAR`フォルダから実行します。

```bash
source .venv/bin/activate
python3 realtime_pnp.py --list-cameras
```

macOSからカメラアクセス確認が表示された場合は許可します。見つからない場合は「システム設定 → プライバシーとセキュリティ → カメラ」で、使用しているTerminalまたはPythonにカメラアクセスを許可してください。現在の既定は、フォーカス挙動を確認済みの`cv2.VideoCapture(camera_index, cv2.CAP_AVFOUNDATION)`によるOpenCV直接取得です。

### 2. まず近似内部パラメータでライブ確認

```bash
python3 realtime_pnp.py --camera 0
```

reference-guided方式をTerminalから明示する場合は次のとおりです。

```bash
python3 realtime_pnp.py \
  --camera 1 \
  --matching-mode reference \
  --ransac-threshold 8 \
  --iterations 10000
```

既定では、`cv2.VideoCapture(camera_index, cv2.CAP_AVFOUNDATION)`で直接取得したカメラのネイティブ解像度を、縮小せずPnPへ渡します。解像度・バッファ・autofocusプロパティは変更しません。Terminalの既定処理上限は5fps、VS Code Mainは追跡を滑らかにするため15fps、水平画角は65度の近似値です。表示ウィンドウで`Q`または`Esc`を押すと終了します。別のカメラ番号なら`--camera 1`などに変更します。

以前に一瞬localizationできた際の取得・マッチング条件を正確に再現する場合は、次のプリセットを使用します。

```bash
python3 realtime_pnp.py --camera 1 --previous-success-settings
```

このプリセットは、FFmpeg導入前のOpenCV/AVFoundation直接読取、ネイティブ解像度、縮小なし、5fps、追跡なし、Lowe ratio 0.75、RANSAC 4px、最小inlier 20点へ固定します。フォーカスゲートとRAW診断画面は無効です。通常の`python3 realtime_pnp.py --camera 1`は同じカメラ取得条件にtemporal trackingを追加した構成です。

バックグラウンドで最新フレームだけを保持する比較経路は`--capture-backend opencv-latest`、FFmpeg経路は`--capture-backend ffmpeg`で明示できます。フォーカスゲートは既定では無効で、必要な場合だけ`--min-focus-score 15`のように指定します。MPRは姿勢推定に使った同一フレームへ重畳します。

RAW比較が必要な場合だけ`--raw-preview`を追加します。これは取得フレームを、リサイズ・focus判定・SIFT・PnP・描画より前にそのまま`imshow()`する診断画面です。

画面上部にはPnPの`matches`、`inliers`、MPR状態に加えて、カメラFPS、実処理FPS、最新フレームへ追いつくために捨てたフレーム数、キュー滞留時間、アプリ内遅延、SIFT・matching・PnP・MPR・3Dデバッグ描画の個別時間、SIFT keypoint数、中央領域の相対的な`center focus`値、入力/処理解像度、判定閾値を表示します。`center focus`は同じ構図で値が高いほど鮮明です。絶対的な合否値ではないため、カメラを静止してAFが落ち着く前後の比較に使います。`app latency`はFFmpegでフレームを復号してから表示処理が終わるまでの値で、iPhoneの撮像・エンコード・無線転送時間は含みません。`latest-frame drops`は異常ではなく、古い映像を順番に処理して遅延が増えないよう意図的に破棄した累積数です。緑点がRANSAC inlier、赤点がoutlier、黄色枠内の半透明グレースケール画像がMPRです。

MPR有効時はカメラ画面に`MPR Slice x0.1%`と`MPR Opacity %`のトラックバーが表示されます。断面位置はカメラ側の手前面0%から奥面100%を基準とし、手前側−100%から奥側150%まで0.1%刻みで移動できます。macOSで負値トラックバーに依存しないよう、UI上の`0〜2500`を内部で`-1000〜1500`へ変換します。UI値の`0 = -100%`、`1000 = 手前面0%`、`1500 = 中央50%`、`2000 = 奥面100%`、`2500 = 奥側150%`です。断面探索範囲にはモデルboxではなくMHA全体のboundsを使用します。データ範囲外まで送った場合は空の断面になります。透過率は0～100%です。

MPR面の外枠は表示しません。断面はカメラの中央光線ではなくCTボリューム全体を基準に配置されるため、対象が画面中央から外れても画面内にあるCT断面は重畳されます。

距離計測時は`Measure Zoom +100%`トラックバーで1倍から12倍まで拡大できます。計測の1点目を左クリックすると、その位置が自動的に拡大中心になります。2点目では中心を動かさず、計測結果を表示します。`Shift+左クリック`またはホイール操作でも拡大中心を変更できます。拡大後の左クリック座標は元のMPR座標へ逆変換されるため、距離の単位と計算縮尺は変わりません。右クリックで計測点をクリアします。
計測点は左ボタンを離した時点で確定します。macOSが発行するダブルクリックの重複イベントは同一の1点として扱います。

断面上の距離は画像上で直接計測します。MPRが表示されている状態で左クリックした点を始点、2回目の左クリックを終点として、画像座標を断面座標へ逆変換した距離を表示します。3回目の左クリックで新しい計測を開始し、右クリックで消去します。単位は`model-coordinate.json`のmillimeter座標に基づくmmです。これはMPR断面内の距離であり、画面上の実物との絶対位置・寸法精度評価にはカメラキャリブレーションが必要です。

3Dマッチ範囲のデバッグ画面は既定で有効ですが、PnP処理を妨げないよう2Hzだけ更新します。不要なら`--no-3d`で停止できます。マッチングより低遅延を優先する場合は次を使います。

```bash
python3 realtime_pnp.py --camera 1 --max-processing-width 1280 --process-fps 10 --no-3d
```

縮小すると小さな模様のSIFTマッチ数が減る場合があります。まず既定の元解像度で`keypoints`、`matches`、`inliers`を確認し、十分な余裕がある場合だけ1280pxへ下げます。

同時に`ViewSync Live 3D Match Coverage`ウィンドウを表示します。灰色がFeature Map全体、緑が現在のPnP inlier、赤がoutlier、オレンジがPnP未成立の候補match、黄色線が対象boxです。`A/D`で水平回転、`W/S`で上下回転、`R`で初期視点へ戻せます。不要な場合だけ`--no-3d`を付けます。

### 3. 正確な重畳用にカメラをキャリブレーション

連係カメラを通常のMacカメラとして読む場合、OpenCVはiPhoneの正確な`fx, fy, cx, cy`を取得できません。近似値のままでもlocalization試験はできますが、MPRの画素位置と位置誤差の評価には使えません。

9×6の「内側コーナー」を持つチェッカーボードを用意し、次を実行します。

```bash
python3 calibrate_camera.py --camera 0
```

ボードの距離、傾き、画面内位置を変えながら、検出枠が出た状態でSpaceを15回押します。`C`で早期確定、`R`で撮り直し、`Q`で中止できます。結果は`output_colmap_image/iphone_camera_calibration.npz`へ保存されます。

その後は同じカメラ、同じ解像度、同じズームで次を実行します。

```bash
python3 realtime_pnp.py \
  --camera 0 \
  --calibration output_colmap_image/iphone_camera_calibration.npz
```

カメラのズーム、解像度、アスペクト比、手ぶれ補正によるクロップが変わると内部パラメータも変わります。精度確認時はこれらを固定してください。本出力は現段階では研究・QC用であり、臨床判断には使用しません。
