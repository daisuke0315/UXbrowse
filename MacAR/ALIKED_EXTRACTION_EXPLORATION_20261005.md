# ALIKED抽出時間の探索的調査（2026-10-05）

後続の[照合前メモリ解放・反復検証](PHOTO_CACHE_VALIDATION_20261005.md)では、解放ありの18照合を完了し、対応数・姿勢を維持しながらdriver確保量の増大を抑えることを確認した。解放なしは5照合で8GB上限に達して停止し、両条件で20秒抽出は再現しなかった。以下は探索段階の条件・結果として保持する。

## 得られた結論

通常の1600px・2000点のALIKED抽出は、同じ2590の反復で約0.18〜0.24秒。初回準備を含む試行も約0.96秒だった。20秒は通常の画像1枚の計算量だけでは再現しない。

ユーザーがMacARを再起動した前後の**同じ2593**を、既存のruntimeログで比較できた。地図・設定・ROI・候補の対応数・最終rvec/tvecが一致したまま、抽出は21.650秒→0.826秒、照合全体は31.873秒→6.162秒へ短縮。プロセスの状態をリセットすると改善することを実機で確認した。ただし「メモリだけを解放した」対照ではなく、モデル・GPUの準備状態・デバッガ接続状態なども再起動で変わる。

元プロセスのfootprintは19.3G、新プロセスは5.7Gだった。取得時刻はそれぞれ14:09、14:39で照合中ではない。**新プロセスも取得時点では多くのメモリが退避されていたため、idle時のswap量だけで照合中の待ちを断定しない。** メモリ肥大化は引き続き有力だが、20秒をCPUページ復帰、GPU待ち、ネイティブ計算のどれが占めたかは未確定。

## 実験条件と範囲

実行中のMacARは操作せず、同じvenv・torch2.8.0・MPS・最大2000特徴点の調査用プロセスで測定。画像は検証写真の元ファイル。ROIはruntimeログにある実際の切り出し範囲を使用した。GPU driver確保量8GBで打ち切る条件を設定した。サイズ・点数変更は調査用だけで、製品設定・コード・地図を変更していない。

ステージ計測では各区間の前後でMPSを同期するため、通常処理とスケジューリングが異なる。各条件は小規模な探索試験で、性能差の統計的評価ではない。20ms間隔のmemory samplingは短い最大値を見逃し得る。サイズを1024へ変更した試行、点数を500へ変更した試行の精度は評価していない。

## 1. ALIKED内のどこが重いか

実装を確認すると、`extract_dense_map`が画像全体で128成分の特徴マップを作ってから、DKDが2000点を選び、SDDHがdescriptorを作る。特徴点2000点の周辺だけを初めから計算する方式ではない。

2590・1600・2000点の暖機後、メモリ解放ありの1試行：

| 区間 | 実測 |
| --- | ---: |
| 入力変換・GPU転送 | 41.2ms |
| サイズ調整 | 0.7ms |
| 画像全体の特徴マップ | 172.5ms |
| 特徴点選択 | 12.4ms |
| descriptor作成 | 16.4ms |
| 特徴点座標のCPU取得 | 0.2ms |
| 抽出全体 | 244.3ms |

解放なしの暖機後は191.5ms（全画素計算162.3ms）。最初の試行は964.2ms（入力準備149.3ms、全画素計算644.7ms）。通常の初回準備で時間差が出ることは確認できたが、20秒には達しなかった。

1600では全画素特徴マップ処理終了時のcurrent allocationが約1.0GB、初回に観測したcurrent peakは約2.1GB。保存画像や最後の2000点のサイズだけでGPU必要量を見積もれない。

## 2. 点数か画素数か

| 2590の暖機後・解放あり | 全画素計算 | descriptor | driver確保量 |
| --- | ---: | ---: | ---: |
| 1600px / 2000点 | 172.5ms | 16.4ms | 4.20GB |
| 1600px / 500点 | 175.8ms | 4.1ms | 4.12GB |
| 1024px / 2000点 | 68.4ms | 13.0ms | 2.29GB |

500点へ減らすとdescriptor作成は軽くなるが、主要な全画素計算とメモリ量はほぼ同じ。1024にすると全画素計算とメモリ量は減る。ただし精度比較をしていないため、1024を製品の改善策として採用する根拠にはしない。500点条件の全体276.4msと2000点条件244.3msの単発差を、点数削減で遅くなる因果関係とも解釈しない。

## 3. 入力形状と未使用メモリ

2590→2590→2593→2598→2590の順で抽出した。

- 解放なし：driver確保量4.20GB→6.35GBへ増え、その後も6.35GBを保持。
- 各抽出前に`torch.mps.empty_cache()`：driver確保量は各画像で約4.20〜4.46GB。
- 同じ画像・1600・2000点のkeypoint座標SHA-256は、解放あり/なしの5試行すべてで一致。
- 解放なしで6.35GBを保持した状態でも、最後の2590は176.5msで終了。

異なる入力形状による不要割り当ての保持は再現でき、解放で抑えられる。しかし確保量6GB程度だけでは、抽出20秒を再現できなかった。確保量の増加と待ち時間を直接比例させない。

前の同一画像によるモデル読み込み・closeの4回反復では、使用中MPS tensorはclose後0になる一方、driver allocation約4.35GBが残った。gcだけでは減らず、empty_cacheで約97MBへ減る。同じ画像だけのモデル再構築では、無制限な増大は再現しなかった。

## 4. LightGlueが後の抽出を重くするか

2590の同じqueryを、実行時の6候補、登録写真から選んだ別18枚、元の6候補の計30回へ照合した。descriptor照合以外のPnP・QCは実行していない。

- 最初の6候補raw対応数は377 / 393 / 119 / 203 / 362 / 359で、実行時ログと一致。
- driver allocationは約1.36GB→1.37GBで大きく増加しなかった。
- 最後の6照合は約62〜132ms/枚。

この範囲ではLightGlueの反復だけで巨大なGPU確保量や長い待ちは再現できなかった。より多い候補・遮蔽・長時間運用のすべてを否定する試験ではない。初期の別crop試験は`lightglue_other_crop_retain.*`として保持し、同一2590の比較には用いていない。

## 5. 解放を写真照合全体へ入れた場合

調査用プロセスのALIKED呼び出し前だけにempty_cacheを追加し、既存の`localize_photo`をそのまま実行した。1600px・2000点・同じ地図・同じ候補選択・同じQCを維持。

| 写真 | 照合全体 | 結果 |
| --- | ---: | --- |
| 2598 | 10.385秒 | PASS・118 inliers |
| 2590 | 2.605秒 | PASS・322 inliers |

以前の同じ別プロセス結果と候補順、raw/F/XYZ/PnP対応数、最終rvec/tvecが一致。メモリ解放でこの2枚の計算結果は変わらなかった。元の遅いプロセスへ解放を適用した試験ではないので、解放だけで20秒を解消したという証明にはしない。別プロセスの11.67/3.22秒との差も、起動環境・キャッシュ履歴が異なるため厳密な速度改善率には用いない。

## 改善の優先順位

まず1600px・2000点・QCを維持したまま、写真切り替え・照合終了・モデル終了など、GPU処理が一区切りした時点の不要メモリ管理を検証する。毎フレーム解放は対象にせず、反復写真・遮蔽試験・長時間運用でfootprintと抽出時間を記録する。

同時計測には、抽出前のGPU queue同期待ち、入力変換・転送、全画素特徴計算、点選択・descriptor作成、使用中/driver MPS allocation、プロセスfootprint、ページ復帰を含める。これにより、20秒が再発したときの内訳を確定できる。今回の調査では製品へ計測・解放を実装していない。

記録は`output_photo_latency_audit_20261005/`の`restart_comparison_2593.json`、`explore_sizes_*.json`、`lightglue_default_retain.json`、`experimental_cache_release_verification.json`、関連スクリプト・ログに保存。
