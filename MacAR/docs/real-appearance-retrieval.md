# 実写appearance検索：現行仕様と比較履歴（2026-10-04）

## 現行仕様：推奨方式を既定にする

ユーザーの採用指示により、登録実写モードの写真照合・ライブ初期化・全体再探索・近傍view復帰では `gs-real` を使う。3DGS方向候補を維持し、各候補にRC回転差55°以内の実写だけを対象に、実写cropのDINO Top10→パッチ配置で再順位付けし、各2枚（重複なし）をLightGlueへ渡す。候補view数3の既定では最大6実写。姿勢ベース点補充、光学フロー、三角測量XYZ、PnP/QC、CT表示、3DGS仮想画像モードは変更しない。

実写DINO索引は登録地図の保存済みcrop/maskと元画像から作り、`.model_cache/registered_dino/`へ保存する。初回のみ全登録実写の索引を生成し、ブラウザの既存処理欄へ生成枚数を表示する。以後は同じ索引を読み込む。地図・画像のパス、参照archive/RGBのサイズ・更新時刻、encoder/前処理コードでcacheを分離する。地図やRGBを替えた場合は再生成する。XYZを生成・変更する処理ではない。原画像がない、crop/maskが不整合の場合はエラー、不正cacheは再生成し、角度順へ黙って戻さない。

既定のDINOパッチ粗検索で得た同一query特徴を実写選択にも再利用する。その他の粗検索や姿勢からの候補指定では、同じ検出ROIからDINO特徴を1回抽出する。XYZ-only再試行では同じquery・実写候補を再利用する。面除外の固定検証は元PASSの実写をそのまま維持し、検索し直さない。

角度順と実写直接の方式は比較スクリプトに残す。本番UIに追加の方式選択は増やさない。

RGBフォルダは地図の`summary.json:image_dir`を使う。現在使用中の増補地図など、明示フォルダのないCOLMAP形式では、`input_files.images`の`colmap/sparse/0/Images.txt`に対応する`colmap/images`を使う。いずれも実際のRGB・crop/maskが存在し整合することを確認する。

実機確認手順：既存VS Code実行を停止→ **MacAR: Browser Live (3DGS + MPR)** → F5 → 新URLで登録実写モードを開始。初回索引の枚数進行、写真2593の照合、ライブ初期PASS→周回→ロスト時の再探索、面除外で元実写の固定、3DGS仮想画像モードの維持を確認する。実機確認の結果は実装後に追記する。

## 採用前の比較履歴と範囲

比較時点の本番は、3DGS/DINOの方向候補からRC姿勢の近い実写を選び、ALIKED/LightGlue・三角測量XYZ・PnP/QCへ進んでいた。以下はこの角度順をbaselineとしたオフライン比較の履歴。比較実施時には本番の既定を変更していなかった。

比較の主仮説は「3DGSの方向候補を維持し、その方向と整合する実写を、角度の近さではなく対象cropのappearanceで選ぶと、照合に適した実写を選べる」。比較スクリプトはオフライン専用で、同じ登録地図・写真・ROI・ALIKED特徴・幾何検証・PnP・領域別姿勢採点・QCを使う。

比較する3条件：

1. `gs-angle`：現行Top3仮想viewから各2枚、最大6枚の実写を角度順に選ぶ。
2. `real-direct`：登録実写cropのDINO全体類似度Top10をパッチ配置で再順位付けし、上位6枚を直接照合する。方向QCの比較先は各実写に姿勢が最も近い既存GS view。ライブ画像のGS検索による独立方向制約はない。この違いを隠して精度改善と解釈しない。
3. `gs-real`：現行Top3仮想viewを固定し、各viewとのRC回転差55°以内の実写をDINO全体類似度Top10→パッチ再順位付けで並べ、各2枚（重複なし）、最大6枚を照合する。方向QCは元の候補GS viewを使う。

実写索引は保存済みobject crop/maskから生成した620枚のDINO特徴を利用する。画像背景もcrop内には残り得る。GS detectorによるライブROI・224正方形letterbox・16×16 DINO patch・前景maskは全条件共通。AIを再学習しない。既存索引は元実験の地図SHA・モデルコード・名前・形状との整合を検査して使用する。原画像・地図・既存索引は変更しない。

## 評価条件

- 既存の12検証写真と、RC姿勢で事前選定済みの12登録写真をすべて比較する。登録写真は自身と±5フレームを参照候補から除く。再構成に使われた写真・近接動画なので独立holdoutとは呼ばない。
- 最大6参照、早期終了なし、追加Top10探索・XYZ-only/明度再試行なしで候補選択の効果を分離する。QCを緩めない。全条件は同じクエリALIKED特徴を共有する。
- 各条件のローカル照合開始時に同じ乱数seedを設定する。候補集合・順序の違いに伴うRANSAC仮説生成の影響は残る。各写真は別MPSプロセス。最初にモデルをwarmupし、条件の順序を交替させる。参照特徴のロードcacheは各条件開始前に空にする。
- 粗検索時間・特徴抽出時間・局所照合/PnP/QC時間を別記録する。共通準備を足した合計はcomponent sumであり、独立したライブend-to-end latencyではない。モデル初期化・索引初回生成は除外して明示する。
- 登録写真：実写直接検索のTop1/Top5/Top10方向差、各方式の照合6候補に正解方向が入るか、姿勢回転差、カメラ中心差、QC PASS・AMBIGUOUS率。RC姿勢は推定基準で物理真値ではない。
- 新写真：QC PASS・AMBIGUOUS率、事前記録された面方向区間との整合、時間、支持領域数。面方向一致は精密な姿勢正解・CT位置精度ではない。
- 失敗・悪化も全例を保存する。候補選択の新規性や最適性を、この小規模データだけで主張しない。

## 比較結果と判断

24枚・各条件2回の144試行を完了。新写真のQC PASSは現行11/12、実写直接10/12、方向制約＋実写検索11/12。登録写真のRC姿勢との比較では、現行の中心位置差最大17.96が、両実写検索で最大4.59 map unitsへ減った。方向制約＋実写検索は、今回の精度・頑健性優先の推奨とする。ただし新写真の成功率向上・CT位置精度向上・ライブ速度向上の証明ではない。現行も方向制約＋実写検索もIMG_2598には失敗する。

新写真の処理成分合計中央値は比較時の現行2.24秒、実写直接1.74秒、方向制約＋実写検索2.17秒。登録写真では1.69秒、1.83秒、1.79秒。方向制約付き実写順位付け自体に約350〜370 msを要し、一律の高速化にはなっていない。比較時点では本番の既定を維持した。その後ユーザーの指示で、上記現行仕様として方向制約＋実写検索を採用した。
